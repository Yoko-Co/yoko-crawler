# Yoko Crawler - Agent Instructions

## Project

Yoko Crawler — a Python/FastAPI service that runs Scrapy spiders as subprocesses to crawl websites and return discovered URLs as NDJSON. It serves as the backend for the Yoko 301s WordPress plugin's "Crawl Site" feature.

## Architecture

- **FastAPI app** (`main.py`) — API endpoints, lifespan management, single uvicorn worker (in-memory state)
- **Job Manager** (`job_manager.py`) — in-memory job dict with asyncio.Lock, max 3 concurrent crawls
- **Scrapy subprocess** — each crawl runs via `asyncio.create_subprocess_exec`, writes JSONL results and atomic status.json
- **Progress extension** (`stats_extension.py`) — Scrapy extension that writes progress to a status file every 3s. A wholesale bot-block (all-403) is NOT failed here: the crawl completes and emits its 403 rows, and the consumer (yoko-corpus) owns the blocked-crawl policy — it reads the forbidden ratio to retry with browser impersonation and, if still blocked, presents an honest "we couldn't read this site" report; failing the crawl would deny it both. Only a crawl that reached NO PAGE OF THE SITE is failed as a genuine empty result — since #102 that includes a crawl whose only responses were seeding traffic (robots.txt, sitemaps, probes), which is not "nothing fetched" but is equally not an inventory, and its cause is classified into a structured `failure_reason` token (issue #44) the corpus maps onto its own `failure_class`: `ssrf_blocked` (every host SSRF-blocked), `unreachable` (0 pages + `downloader/exception_count > 0` — DNS/connection failure, i.e. a mistyped/wrong address), `crawl_error` (an abnormal Scrapy close), or **`seeding_incomplete` (#102)** — robots.txt responded but the start URL was never emitted, so the crawl reached no page of the site. That shape is invisible to the empty-crawl guards, which require `response_received_count == 0`: robots.txt answering makes the count 1, so the crawl used to sail through as `completed` with a one-row "inventory" that is robots.txt itself — the most deceptive shape available, and previously only a log line. It is gated on `completed` so `ssrf_blocked`/`unreachable` still win where they apply (they name the cause; this names the symptom), and it does NOT fire for a robots-restricted site, because `_start_url_requests` is deliberately not routed through `_schedule` and a `Disallow: /` site still emits and counts its start URL. **`spider_init_error` (#98)** is the one token NOT set by `ProgressWriter`: it is written by `run_spider` itself when the spider fails to CONSTRUCT, because `ProgressWriter` attaches on `spider_opened` and that never fires. Scrapy routes an `__init__`/`from_crawler` exception into the Deferred `crawl()` returns; with no errback it goes UNHANDLED (traceback logged at GC time, after anything main() prints), `process.start()` returns normally and the script exits 0 — so `job_manager` saw its own pre-spawn `queued` stub, missed the terminal-status branch and reported the crawl **completed with zero pages**. Measured on the real tree before the fix. `run_spider` now attaches an errback, writes the classified failure and exits non-zero; `job_manager` independently treats exit 0 with no output AND no status of the spider's own as failed. That second guard is a REGRESSION guard, not a wider net: an earlier draft justified it with SIGKILL/OOM/failed-exec, all of which were disproven by execution (each yields a NON-ZERO returncode and lands on the generic branch instead). Its real value is holding if a future edit drops the errback, plus a SIGTERM inside the startup window that leaves the Deferred unfired. It is corroborated against the FEED — a spider that never constructed cannot have emitted a row — because `ProgressWriter._write_status` swallows OSError, so a read-only status path would otherwise make a 5,000-page crawl look like one that never started. Otherwise `failure_reason` is set only in `ProgressWriter.spider_closed`, so it's `null` on any crawl that fetched at least one page AND on a **job-manager-level** failure that never reaches the Scrapy close (spawn failure / watchdog timeout / monitor crash — `status: failed`, `failure_reason: null`); consumers treat `null` as "unclassified", not "succeeded", and key on `status`/`failure_reason` rather than `close_reason` (which stays `"finished"` on a reclassified empty crawl). Surfaced on `status.json` and threaded through `job_manager.get_status_response` to `GET /crawl/{id}`. Bot-wall challenge pages are recognized in the spider (see below) and counted via the `waf_challenge_count` stat.
- **Bot-wall (WAF) challenge handling + block legibility** (`website_spider.py`, `stats_extension.py`) — a Cloudflare/WAF challenge page is real HTML with a body, so without a guard the crawler would mine its markup as "content" and follow its links (e.g. Kinsta's `?ki-cf-botcl=1`), polluting the crawl with the wall's own pages. `_is_waf_challenge(response)` flags a challenge on a `403`/`429`/`503` status **plus** a Cloudflare signal: the `cf-mitigated` header (reliable — CF stamps it only on responses IT generated; INCOSE's `/setdb-login/` returns `403 cf-mitigated: challenge`), OR `cf-ray` + `server: cloudflare` **with no origin fingerprint**. The origin-fingerprint guard (`_has_origin_fingerprint`: `x-powered-by`/`x-aspnet-version`/… or a non-CF `Set-Cookie`) is what keeps a **proxied origin 403** (member-restricted content we DO want inventoried) out of the wall bucket on CF-fronted sites, where every response also carries `cf-ray`. A challenge row is still emitted (its status is the corpus's signal) but gets empty enrichment and its links aren't followed. Observability, not a verdict — we can't recover intent from one blocked fetch: `waf_challenge_count` (CF wall) vs `origin_forbidden_count` (origin 403) plus a full HTTP `status_counts` histogram are surfaced in the status file's `blocking` section for the corpus/frontend; the crawl still `completed`s (yoko-corpus owns the block policy). Cloudflare/Kinsta challenge query tokens (`ki-cf-botcl`, `__cf_chl_*`) are in `UNWANTED_PARAMS` so a stray challenge link isn't recorded as a distinct page.
- **Domain validator** (`domain_validator.py`) — SSRF prevention: format check + async DNS range-check at submit time, with a synchronous re-check at crawl-worker startup. `DomainValidationError` carries a structured `code` (issue #48: `unresolvable` / `private_address` / `is_ip` / `bad_format`), surfaced on the `POST /crawl` `422` body as `{"detail": <msg>, "code": <code>}` (via a `JSONResponse` so `detail` stays a string) so the corpus classifies a mistyped-domain rejection by code instead of scraping the prose
- **SSRF guard** (`ssrf_guard.py`) — downloader middleware that re-resolves each request's host at fetch time and drops any resolving to a blocked/reserved range (covers both the default and curl_cffi download handlers). It also refuses any **non-http(s) scheme** outright (`ssrf_guard/blocked_scheme`, issue #89) — a separate question from the address check, which asks only whether a HOSTNAME resolves somewhere reserved and therefore waves through `file://<a-real-public-domain>/etc/passwd`
- **Fetchable schemes** (`website_spider.py`, issue #89) — `is_internal` refuses anything but `http`/`https` **before** comparing the host, because a host match is not a safety property: Scrapy registers handlers for `file`/`ftp`/`s3`/`data`, and `FileDownloadHandler` resolves through `w3lib.url.file_uri_to_path`, which DISCARDS the host and reads the bare local path. Three intake paths take a value the remote server controls with `is_internal` as their only validation — a `Location:` on a robots.txt redirect, a `Sitemap:` line, and a sitemap `<loc>` (the `<a href>` path was already screened by `_NONNAV_SCHEMES`). The gate lives in `is_internal` rather than at each call site so it fails closed: a call site nobody enumerated cannot open it. It also turns a protocol-relative `//host/sitemap.xml` — which `Sitemap:`/`<loc>` do NOT urljoin — from a `ValueError: Missing scheme` raised mid-parse into a clean skip. Refusing a hostile robots redirect must still SEED (`test_a_hostile_robots_redirect_is_refused_AND_still_seeds`): a zero-page crawl would be strictly worse than the redirect
- **TLS impersonation** (`tls_impersonate.py`) — Scrapy downloader middleware that tags each request with a current browser TLS fingerprint (via curl_cffi / `scrapy-impersonate`) plus a matching User-Agent — a **fingerprint-compatibility** measure, since JA3/JA4 WAFs `403` the default Scrapy/curl fingerprint outright regardless of intent (paired with obeying robots/`nofollow`/`meta robots`; we do NOT punch through an active challenge). `IMPERSONATE_CHOICES` is the single source of truth for the `--impersonate` CLI flag and the API field. **Timeouts (#88):** scrapy-impersonate forwards no timeout to curl_cffi and reads neither `download_timeout` nor `DOWNLOAD_TIMEOUT`, so this path silently ran on curl_cffi's undeclared 30s session default -- a bound nobody chose, invisible in `run_spider.py`, and free to move when the dependency changes. `ImpersonateMiddleware._forward_download_timeout` now copies `meta["download_timeout"]` into `impersonate_args["timeout"]` (it runs at priority 725, after `DownloadTimeoutMiddleware` at 350, so the meta is already populated), giving ONE timeout mechanism for both download paths and letting per-request overrides like the robots budget work unchanged. `run_spider` declares `DOWNLOAD_TIMEOUT: 60` for impersonated crawls -- not Scrapy's 180s, because `--impersonate` pairs with `--profile presale` (`CONCURRENT_REQUESTS: 1`) where one hung request stalls the whole crawl; and not the old 30s, which is inside the range a slow-but-real page on a WAF-fronted site can take, so it was recording real pages as transport failures
- **Sitemap discovery** (`website_spider.py`, issue #77) — sitemaps come from `Sitemap:` lines in robots.txt AND, when robots.txt names none (or could not be read), from probes of the conventional locations (`/sitemap_index.xml`, `/sitemap.xml`, `/wp-sitemap.xml`, `/sitemap-index.xml`). Probes are skipped for robots-disallowed paths (`seeding/sitemap_probes_disallowed` — a non-zero value is why `sitemap_probes_sent` is 0, which would otherwise be ambiguous). A probe uses its own callback (`parse_sitemap_probe`) that emits NO row unless the body's ROOT element is a sitemap: `parse_sitemap` emits a row per response, which is right for a URL the site advertised and wrong for one we guessed, and phantom 404s would surface in the report as "broken links on the site". A guessed sitemap's URLs carry `meta["guessed_source"]`, and a DEAD one is emitted as a `guessed_sitemap_dead` skip row rather than a 404 page row — a stale sitemap left over from a previous platform would otherwise inflate `page_count` and push `blocked_fraction` past the `wholesale_blocked` threshold, reporting "we couldn't read this site" about a site we read perfectly. A sitemap the site ADVERTISED is a positive assertion of currency, so its dead URLs stay normal 404s.
- **robots.txt obedience** (`website_spider.py`, issues #57/#59) — the site's robots.txt is the crawl's ONLY seed and a **prerequisite** of it (issue #76): it is parsed with **Protego** in `parse_robots`, which then emits the start URL, so no page URL is ever scheduled before the rules are known. **Disallow** rules gate scheduling: `is_robots_disallowed(url)` (checked in `_schedule`, stat `robots_disallowed_skipped`) keeps us out of `Disallow: /search/` facet traps and anything else the site marks off-limits. **Crawl-delay** is honored per-host: `_apply_crawl_delay` paces at `max(our DOWNLOAD_DELAY, min(asked, cap))` — it RAISES AutoThrottle's `mindelay` floor (so the adaptive throttle can't lower back below the site's ask) and bumps the live download slot; capped at `YOKO_CRAWL_MAX_ROBOTS_DELAY` (default 10s, env-tunable) so a pathological delay can't blow the crawl budget (clamps are logged; a slow crawl finalizes partial, honestly labelled via close_reason). We obey the `ROBOTS_USER_AGENT = "yoko-crawler"` group, which falls back to the catch-all `*` (and honors a rule that names us). All best-effort/allow-all for a site without a robots.txt, or when it could not be FETCHED (`seeding/robots_failed` — a transport failure means we could not read a "no", so we do not invent one), so it only ever ADDS a skip. **Readability (#97):** `robots_failed` fires on TRANSPORT failure only, so the far commoner route to an unjustified allow-all — a 403/503 robots.txt, which returns an ordinary response whose body the `status == 200` gate discards — was counted nowhere. `_record_robots_readability` now classifies every route into ONE per-crawl outcome on `restrictions.robots_readability`: `parsed` (we hold rules), `absent` (404/410 ONLY), `unreadable` (transport failure, any other non-200, or an undecodable body: rules may exist and we did not see them), `unknown` (never resolved), `not_recorded` (the recorder itself never ran — a tripwire, logged loudly, kept distinct so a broken instrument cannot hide inside a legitimate outcome). **We are deliberately STRICTER than RFC 9309 here, which is the opposite of what an earlier draft of this note claimed:** the RFC treats most 4xx as "unavailable" and licenses allow-all on a 403, and treats 5xx as reason NOT to. We put 403 in `unreadable` because in our population a 403 on robots.txt is usually an edge WAF refusing *us*, not an origin declaring it has no rules — that reasoning is ours, not the RFC's. `cf_wall` is CLOUDFLARE-SPECIFIC (`_is_waf_challenge` keys on cf-mitigated / cf-ray + Server), so read it as a FLOOR on edge refusals: Sucuri/Akamai/AWS/Imperva walls land in the not-CF bucket, and vendor-agnostic detection is #100. `rules_from_state` marks a refused session that still holds rules restored from an earlier one, so a refusal and the rules we carry are both recorded rather than one erasing the other. OBSERVED, not a verdict — it changes no crawl behaviour; whether an `unreadable` crawl should STOP rather than proceed allow-all is the open posture call in #97, deliberately left to be answered from these counts. Corpus carries it through `_fold_restrictions` onto the summary: `robots_readability` is best-outcome-wins (one session that read the rules settles the crawl) and `robots_readability_unreadable_sessions` COUNTS the refused sessions, because the outcome alone cannot — a site that blocked us for thirty-nine sessions after one good one is honestly `parsed`, and the count is the only place those thirty-nine survive. Ties break toward `unreadable` over `absent`: under-counting refusals is the one bias that would settle #97's posture question the wrong way. **Fetch budget (#82):** because robots.txt is the only seed, a black-holed host stalled the whole crawl — 3 x Scrapy's 180s DOWNLOAD_TIMEOUT = 540s of a 7200s session with zero pages, and under `--profile presale` (`CONCURRENT_REQUESTS: 1`) that is paid EVERY session, not just the first. `_robots_budget_meta()` bounds every robots.txt fetch, every redirect hop and every sitemap probe at `robots_download_timeout` (default 60s, operator-tunable via `YOKO_CRAWL_ROBOTS_TIMEOUT` within a **hard floor of 60s and ceiling of 600s**, issue #92). Below the floor is logged and IGNORED, because a shorter budget does not speed a crawl up — it makes a slow site look like one with no robots.txt and the crawl proceeds allow-all. Above the ceiling is logged and CLAMPED, because robots.txt is the only seed: the pre-page stall is `(ROBOTS_MAX_RETRY_TIMES + 1) x budget`, multiplied again by redirect hops and sitemap probes, and past the ceiling it outruns `job_manager`'s 7500s watchdog, which SIGKILLs the crawl into `failed` with a null `failure_reason` — strictly worse than the allow-all the floor prevents. Both bounds are MODULE constants, not class attributes, because Scrapy assigns `-a` spider args into `self.__dict__` and an instance-read floor was measurably defeatable by `-a DEFAULT_ROBOTS_DOWNLOAD_TIMEOUT=1`. **Observability (#99):** both robots knobs report their RESOLVED values on `restrictions.knobs` — `{effective, requested, disposition}` each, where `disposition` is `default`/`raised`/`floored`/`clamped`/`invalid`/`unknown`. The disposition is the load-bearing field, not the number: a REFUSED value and an unset one produce the same effective budget, so without it a knob that silently did nothing is indistinguishable from one that worked, and the only prior record was a log line on a hand-managed droplet. `requested` is the RAW string, since `int(float("59.9"))` prints as 59 and an operator debugging their own setting needs what they typed. Published from `start()`, NOT from `__init__`: `Spider.from_crawler` calls `cls(...)` and only then `_set_crawler`, so a stat written during construction is dropped in silence — a test pins that premise, and another pins that `start()` actually calls the publisher, because deleting the call site left the suite green) with `ROBOTS_MAX_RETRY_TIMES` (2) attempts, writing THREE meta keys because the two download paths read different ones — `download_timeout` + `max_retry_times` for Scrapy, `impersonate_args` for scrapy-impersonate, which reads neither key itself. Since **#88** `ImpersonateMiddleware` forwards `download_timeout` onto that path, so the explicit `impersonate_args` here is no longer the only route to curl -- but it is not redundant: it is what keeps the robots gate's bound independent of the page bound (the forwarder uses `setdefault`, so this wins), and the two being equal today is a coincidence of the numbers, not a property. Sized deliberately generously and NOT tuned down: timing out routes to `robots_failed`, which proceeds allow-all, so too short a bound silently converts "this site was slow" into "this site has no robots.txt" and crawls a site that said Disallow. Both the timeout and the attempt count are pinned per-request rather than inherited, so whether we honour a Disallow cannot depend on which `--impersonate` flag the operator passed. The rules are persisted into `self.state` and restored in `_bind_dedup_state`, because JOBDIR carries the frontier but not spider attributes and the gate would otherwise be open at the start of every RESUMED session. Seeding is two-phase, so `seeding/start_urls_emitted` is tripwired separately: robots fetched + start URL never emitted is a crawl that reached no page of the site and would otherwise report `completed`. Since **#102** that tripwire also FAILS the crawl as `seeding_incomplete` — but only when every response the session received was seeding traffic (robots.txt, sitemaps, probes). That bound is load-bearing: the condition is a #76-era LOG predicate, and on its own it fails a RESUMED session that restored a full frontier and crawled the site fine, since `start_urls_emitted` is per-session and `closespider_timeout`/`itemcount` — how every session of the corpus's multi-session path ends — are COMPLETED reasons. Measured at 4,000 pages before the bound was added. It under-counts seeding responses by design, so an unlisted category makes the guard SILENT rather than wrong, and `YOKO_CRAWL_FAIL_SEEDING_INCOMPLETE=0` drops the failure while keeping the log. **Restriction observability (#74):** the URL classes we deliberately skip (`robots_disallowed`, `login_gated`, `infra`, `facet_capped`, `nofollow_links`, `meta_nofollow_pages`) and the honored-vs-requested robots.txt Crawl-delay are surfaced in the status file's `restrictions` section and forwarded by `job_manager` on `GET /crawl/{id}`, alongside `blocking`. Same design rule — OBSERVED counts, not a verdict; the consumer decides what they mean. `robots_disallowed` large relative to pages crawled means the crawl is not an inventory (gastro.org: `Disallow: /` reduced 2,347 URLs to a single fetched PAGE, still reporting `completed` and rendering as "a Simple site". Strictly the crawl holds two rows — robots.txt is emitted as its own row as well — which matters whenever a guard is tempted to key on the row count; #102 keys on seeding-vs-page responses instead, for exactly that reason). Complements the existing browser-directive obedience (`rel=nofollow`/`ugc`/`sponsored`, `<meta name=robots>` nofollow, `/cdn-cgi/` infra) and the order-insensitive facet dedup (`facet_dedup_key`/`max_facet_depth`, #49)
- **User-Agent override** (`--user-agent`, `CrawlRequest.user_agent`) — overrides the UA on all requests (via the `USER_AGENT` setting; survives impersonation since `ImpersonateMiddleware` sets UA with `setdefault`). CR/LF/NUL are rejected by the `CrawlRequest` validator so a crafted value can't inject a header. (The old `cf_clearance`/raw-cookie injection was removed: on the deployed datacenter IP it never cleared a challenge — the block is IP-reputation driven — so it was dead weight that obscured intent. `COOKIES_ENABLED` stays on so the *site's own* session/affinity cookies persist across the crawl.)
- **Content extraction** (`content_extractor.py`) — pure, per-response helpers the spider calls to produce the additive NDJSON enrichment: trafilatura locates the main region and supplies the text to hash (counts run over the **original** lxml DOM, since trafilatura strips `<form>`/`<iframe>`); structural counts (when the main region can't be located, counts fall back to the `<body>` but with **site chrome de-chromed** — nav/aside/header/footer + banner/contentinfo/navigation/search roles — so the theme doesn't inflate them, issue #9; guarded against eating real content: chrome inside an `<article>`, or holding an `<article>`/`<main>` or substantial non-link prose, is kept; `svg` is treated as non-content); surprise-embed signals; interactive-**component** detection (sliders/carousels/accordions/tabs/galleries via container markers, `component_count`, issue #12); and a stable normalized SHA-256 `content_hash`. trafilatura's SIGALRM timeout is disabled (`EXTRACTION_TIMEOUT=0`) because it can't run off Scrapy's main thread. **`structure_hash`** (issue #36) is the content-free LAYOUT fingerprint downstream clusters into templates ("N pages across ~M templates"): the depth-limited block-tag skeleton of the content root, chrome (`nav`/`header`/`footer`) and inline tags dropped, **prose blocks** (p/hN/blockquote/pre/hr) collapsed to one opaque `prose` token so an author adding a subheading/paragraph doesn't split a template (issue #35 — validated on openprimaries' Primary Buzz series, 7→4 hashes; `ul`/`ol`/tables/forms stay granular, the safe direction), and consecutive identical sibling runs collapsed. NOTE: the prose collapse is a deliberate fingerprint-EPOCH change (every `structure_hash` shifts, so stored crawls re-cluster on next analyze). Because lxml/libxml2 is **not** an HTML5 parser, a theme with unclosed tags in its header (an unclosed `<div>`/`<li>` in a mega-menu — common) leaves that element open and the parser nests the WHOLE page inside `<header>`, even though the source closed it; the skeleton then sees only chrome and every page of the site fingerprints as `""` → no template clusters → the discovery report reads "Not analyzed" over a complete crawl (Sarah, sais.org). So when the ordinary descent yields NO structure, `structure_hash` retries from the page's own semantic roots (`<main>` → `[role=main]` → a LONE `<article>`, `_semantic_content_roots`), found document-wide so the mis-nesting can't hide them. Four rules there are load-bearing, each one a bug that was found by review or by checking live pages: (1) the descent stays **primary**, so every page that fingerprints today keeps a byte-identical hash — verified across live well-formed sites; (2) candidates are a **list**, tried until one yields a real skeleton — an empty SPA placeholder `<main id=root></main>` beside the real `<article>` otherwise reproduces the very `""` this exists to prevent; (3) they are taken in **document order and capped** (`_MAX_ROOT_CANDIDATES`), never ranked by subtree size — ranking walked every candidate whole, so a hostile 2.4MB page of 250 nested `<main>`s (libxml2 caps nesting near 255) spent **15s** in `structure_hash` versus 0.21s, and made the choice content-length dependent so one template split as pages grew; (4) `<footer>` is the ONLY excluded ancestor (`_RESCUE_EXCLUDED_ANCESTORS`) — a footer "related story" `<article>` is page-invariant theme markup that would merge every rootless page into one bogus template, while `<header>`/`<nav>` must stay eligible because being buried under them IS the bug (on real sais.org pages the swallowed `<main>` sits under `nav.nav__main--menu` inside `header.header`; excluding `<nav>` re-broke all 525 pages, which a synthetic fixture — nesting only under `<header>` — did not reveal). There is deliberately **no** "descend into chrome" fallback either: on such a document that lands in the nav, identical on every page, and one 525-page "template" is a confident under-quote; no fingerprint beats a false merge
- **Embed allowlist** (`embed_allowlist.py`) — configurable benign-embed host allowlist (env `YOKO_CRAWL_BENIGN_EMBEDS`, additive) driving `embed_count_nonbenign`
- **Auth** (`auth.py`) — Bearer token via `secrets.compare_digest`

## NDJSON contract

The enrichment field names have a single source of truth: `ENRICHMENT_FIELD_NAMES` in `content_extractor.py`. `website_spider` builds its zero/empty row defaults from `content_extractor.empty_enrichment()`, and `run_spider.BASE_FEED_FIELDS` is the original five fields plus `ENRICHMENT_FIELD_NAMES` — so adding a field in one place propagates everywhere (a sync test in `tests/test_website_spider.py::TestSchemaSync` guards this). New fields are additive only — the original five (`url`, `status`, `last_modified`, `redirected_to`, `referrer`) never change. `content_text` is the one conditional column (present only under `--emit-content`). See the README "Output format" section for field semantics and the hash/normalization spec.

## Deployment

The service runs the same Python code in either environment:

### VPS (primary)
- App code: `/opt/yoko-crawl/app/`
- Virtualenv: `/opt/yoko-crawl/venv/`
- Result files: `/opt/yoko-crawl/results/`
- Reverse proxy: Caddy (automatic TLS)
- Process manager: systemd (`yoko-crawl.service`)
- Guide: `docs/vps-deployment.md`

### Docker (alternative)
- Reverse proxy: nginx (manual TLS via certbot)
- Result files: `/data/results` (set via `YOKO_CRAWL_RESULTS_DIR` env var)
- Guide: `docs/deployment-checklist.md`
